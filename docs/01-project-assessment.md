# 项目评估与最小重构建议

## 1. 当前项目是否适合继续沿用

适合。

原因很简单：

1. 当前项目是一个干净的 Spring Boot + JPA + Web + MySQL 基础工程。
2. 还没有复杂历史代码，不存在“改旧系统”的负担。
3. 技术栈和你的目标基本一致，后续只需要补齐 Swagger、JWT、参数校验等常用能力。
4. 对于“适合写进 Java 后端实习简历的小型完整项目”来说，这种起步方式很合适。

## 2. 当前项目存在的不足

当前工程能启动，但还不能直接支撑业务开发，主要差这几类东西：

1. 包名和项目信息过于默认
2. 缺少清晰的分层目录
3. 缺少数据库初始化脚本
4. 缺少接口文档工具
5. 缺少登录鉴权能力
6. 缺少统一返回结构和基础异常处理

另外有一个很小但值得提前修正的点：

1. 建表时尽量不要直接使用 `user` 作为业务表名
2. 更建议使用 `app_user`，避免和系统语义混淆

## 3. 最小重构建议

这里强调“最小”，避免一上来做复杂架构。

### 3.1 包名建议

当前包名：

`com.example.interviewdemo`

建议后续改成更像正式项目的名字，例如：

`com.interview.practice`

或者：

`com.yourname.interview`

说明：

- `com.example` 太像教学示例
- 面试时不够正式
- 但这不是阻塞项，可以在正式写业务代码前统一改一次

### 3.2 目录结构建议

建议采用最基础、最好理解的单体分层结构：

```text
src/main/java/com/interview/practice
├─ common        // 通用返回、异常、工具类
├─ config        // Swagger、JWT、MVC 配置
├─ controller    // 接口层
├─ service       // 业务层
├─ repository    // 数据访问层
├─ entity        // 数据库实体
├─ dto           // 请求响应对象
└─ enums         // 枚举
```

这样做的好处：

1. 初学者容易理解
2. 和大多数 Spring Boot 项目风格一致
3. 后续扩展不会乱

### 3.3 依赖建议

当前已有：

1. Spring Web
2. Spring Data JPA
3. MySQL
4. Lombok
5. Test

后续建议补充：

1. `spring-boot-starter-validation`
2. Swagger/OpenAPI
3. JWT 相关依赖

### 3.4 开发顺序建议

建议严格按下面顺序推进，不要跳：

1. 先定表结构
2. 再定接口
3. 再做用户模块
4. 再做题库模块
5. 再做模拟面试模块
6. 再做历史记录模块
7. 最后接 AI 点评报告

原因：

- 用户模块是所有功能入口
- 题库模块是面试模块前置依赖
- AI 点评放最后，最符合“先做可运行主流程”的原则

## 4. 现在不建议做的事

1. 不要急着拆微服务
2. 不要一开始就引入 Redis、MQ
3. 不要先做复杂权限系统
4. 不要先做多角色后台
5. 不要先做文件上传解析

你的目标不是“做一个炫技系统”，而是做一个：

- 可以完整跑通
- 能讲清楚
- 对初学者友好
- 能写进简历并经得起面试追问

## 5. 这一阶段面试时可以怎么讲

可以这样表达：

“我先把项目定位成单体 Spring Boot 后端，避免一开始过度设计。项目初期我优先完成领域建模和接口设计，把核心链路先跑通：用户登录、题库管理、模拟面试、答题记录、AI 报告。这样做的好处是开发节奏清晰，也更符合中小型业务系统的落地方式。”

补充一点，如果面试官追问“你怎么控制复杂度”，你还可以继续说：

“在建模上我做过主动收敛，比如题库只保留题干，不拆标题；分类单独抽成 `category` 表避免用户重复输入；不再额外设计标签体系，而是改成更直接的 `source` 字段表示题目来源。这样可以减少无效复杂度，把精力放在主流程实现上。”
